# Portal template guide

- Portal pages extend `base.html`; `login.html` is a standalone document that includes `partials/theme_boot.html`. Shared components, icons, flash messages, navigation, and row/run fragments live in `partials/`.
- Keep the portal server-rendered and usable when HTMX/CDN JavaScript is unavailable. Search, paging, and mutations remain real links/forms with HTMX as progressive enhancement.
- Mutating handlers return a refreshed fragment for HTMX and a safe redirect/flash for ordinary forms. Match each `hx-target`/swap boundary to the server-rendered partial root.
- A run article is the replacement unit after run actions; avoid rendering the same run through multiple competing template paths.
- Add reusable display logic to `macros.html` or `templating.py` rather than duplicating it across pages. Keep inline SVG definitions centralized in `partials/icons.html`.
- Validate with the relevant `tests/test_api_portal.py` or `tests/test_portal_*.py` file.

## Design principles

- Treat the portal as **“Kanade's Desktop”**: a saturated coloured desktop holds cream content windows with solid chrome title bars, rounded frames, restrained shadows, and the shared three-dot motif. Do not place readable content directly on the coloured ground, and avoid nesting cards where one window boundary already establishes the region.
- When a page contains multiple related windows, integrate them into one window with title-bar tabs rather than stacking separate chrome-topped cards down the page. Each tab represents one coherent section, keeps its count or state visible when useful, and swaps within the shared window so only the active panel owns the content area and its scrolling. Do not create a second row of tab-like controls inside that window or make users scroll the document between sibling sections.
- On wide viewports, keep framed pages bound to `100dvh`: the masthead, page caption, window title bar, and bottom status stay fixed while the window, pane, table, board column, or sidebar that owns the content scrolls. Prefer flex sizing over brittle viewport-height calculations. Phones use ordinary document flow rather than short nested scroll regions, and no-scroll framing must yield when it would make fallback content unreachable.
- Preserve an operational, task-first hierarchy. Keep the current scope and primary state visible; give the main working surface the remaining space; demote one-time explanation before shrinking controls or data. Times and key counts are the loudest row-level values, while recognizable member and boss names lead machine IDs.
- Preserve the boss week's shape. Wide screens use the seven-day board and return space from empty days to busy ones; narrow screens use the seven-cell summary rail plus a readable vertical run list. Scroll horizontally rather than compressing meaningful columns beyond legibility.
- Use the established typography by role: Solway for identity and titles, Zilla Slab for prose and controls, and Sometype Mono for times, IDs, counts, latencies, and aligned numeric data. Use the shared type-scale tokens instead of inventing component-local sizes.
- Use only the shared colour tokens and retain all five browser-local colourways—marigold (default), blossom, periwinkle, coral, and twilight—with System/Light/Dark modes. Stamp preferences before first paint, keep them out of server state, and update every light/dark token set together. The bot's Discord avatar and banner supply portal identity in the masthead, favicon, and login window, with resilient monogram/colour fallbacks.
- Never rely on colour alone for navigation, status, selection, or risk. Pair colour with text, weight, borders, shapes, symbols, and programmatic state; keep visible focus treatment and readable contrast in every colourway and mode.
- Keep responsive navigation predictable: grouped destinations on desktop; Week and Inbox pinned on phones with the remainder in a native disclosure. Frequent actions stay visible, labels name outcomes, destructive actions remain visually separated, and controls must remain keyboard- and touch-usable.
- Keep motion quiet and functional: only a short opacity/transform settle and clear HTMX busy/swap feedback. Do not animate layout, and preserve the reduced-motion override.
