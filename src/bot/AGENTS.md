# Discord adapter guide

- `/style` choices, autocomplete and validation read the live published-profile list; a saved private choice is retained but unavailable and chat falls back to the bundle default.
- Twilight-based and storage-independent: persistence and scheduling are reached only through traits (`CardIndex`, `ReactionSink`, `DeliveryJournal`, `SchedulerService`).
- `transport/`: the `DiscordTransport` trait (`mod.rs`), `TwilightTransport` (`twilight.rs`: 10 s attempt / 30 s call / 2.5 s interaction-response deadlines, ≤4 sends per call), `FakeDiscord` (`fake.rs`, test-support). Every call returns `Delivered`, `DefinitelyRejected` or `Ambiguous` (`outcome.rs`); an ambiguous create may have posted and must never be replayed. Connect failures are `NotSent`. `create_flagged_message` (only `CREATE_FLAGS`; `SILENT` for chat placeholders) and fire-and-forget `trigger_typing` default to `Invalid` unsent: any wrapper transport must delegate them (serve's `LateTransport` does). `FakeDiscord::hold(op)` parks a call mid-flight for tests.
- `mentions.rs` is the only way to build allowed mentions: explicit valid user IDs only, never `@everyone`/roles/replied user; an empty list pings nobody.
- `gateway/`: least-privilege intents matching v4 (`intents.rs`), single-shard `runner.rs` with graceful drain, `close.rs` fatal close reasons (4004, 4010–4014), `status.rs` the connection state health reads (`run_live` takes a prepared router + status). `events/`: guild-scoped routing, ✅/❌ reactions → RSVP via `CardIndex`, roster updates. `EventHandler::handle` runs inline — keep it short and move Discord I/O to `commands::spawn_interaction` or tasks.
- `commands/`: guild registration payloads (`build.rs`), v4 permission gates (`access.rs`), dispatcher with ephemeral refusals, deferred replies, gated autocomplete and redelivery dedupe, and the retained v4 commands (`register_retained`; user decision 2026-09-25). Handlers read through `CommandContext` and write only through the API's shared `Writer` as `member:<id>`/`Surface::Discord` with the interaction id as request id; notices come from the scheduler's outbox, never posted here. Member edits (`/pings`, `/style`, `/nick`; members are not history rows) go through `ReadStore::edit_member_recorded` instead, as the invoker (`member:<id>`, `Surface::Discord`) with no replay key, so an effective edit adds a History `members` row as the admin portal's do. Replies keep v4 texts (`text.rs`); `/rescan` answers "not available" until its port is wired; `/debug ping`/`clear_test`/`header` go through `delivery::DebugDesk` (`delivery/debug/`: journalled `debug_card` effect, `DeliveryTarget::DebugCard`, `debug_cards` rows). Only a run's ping in its home channel is registered and refreshed; any other channel, a sample run (`sample.rs`, in memory only) or a digest is stored as a `sandbox_<kind>` card (display only: no pings, no ✅/❌, run need not exist). Test headers are the seed or an unstored `HeadingRewrite::trial` (every trial writes one Rewrites-log row through `HeadingRewrite::log` with its `TrialOrigin`; reports show the failure code); `/debug header` posts trials unjournalled with no mentions; `/debug reminders` only reads and `/debug materialise` calls the shared writer's idempotent `materialise` (`/debug tick` is an accepted omission: the tick loop has no on-demand seam); `/limits` reads the chat pilot's allowance.
- `delivery/`: `tick.rs` runs v4's order (materialise on rollover → mark_done → attendance recount (V5 only) → draft expiry → notice outbox drain (`notices.rs`) → ownership requests (`owner_requests.rs`: expire after 24 h, post open ones once by source key `owner-request:<id>`, edit decided posts to the outcome) → digest → dispatch) with one clock read and at most one lease per tick, begun lazily (`TickLease`) by the first step that writes to the journal, so an idle tick writes no lease row; dispatch and the notice drain each have their own cap (`max_sends_per_tick`) on claimed sends; `executor.rs` maps outcomes to the journal (Delivered→`bind` with the channel actually used, Ambiguous/bind error→`mark_indeterminate`, NotSent/RateLimited→`release_unsent`, other rejections→`retire_rejected` + alert) and replaces a digest only after confirmed deletion; `alerts.rs` throttles identical admin alerts per hour (`LogAlerts` is the serve destination: structured log); `ports.rs` adapts stores/clock. One failing send never aborts the tick (only lease/backend loss does). Auto-checkpoint and draft expiry failures never abort it either: they raise throttled `CheckpointFailed` / `DraftExpiryFailed` / `AttendanceRecountFailed` alerts and retry next tick. Notices are written to the store's notice outbox by the deciding commit/close itself; `notices.rs` drains them through `Executor::execute_source` (journal `claim_source`, keyed by `(source, ordinal)`), so never enqueue returned notices again. `notice_text.rs` renders them (v4's notice texts byte-exact for the kinds v4 announced); stale (`max_notice_age`), silent and undecodable rows are handled per row and never abort the tick. Rendering and mentions follow `DeliverySettings.attendance`: V4_COMPAT is v4 exactly; V5 adds tallies/expected and morning pings to unknown members only (`docs/notes/attendance.md`). Reminder/digest cards live in `delivery/cards/` (v4 `day_of_card`/`countdown_card`/`digest_card`, art via `ArtSource`, the persona-voiced day-of heading and countdown/digest phrases via the nudge rewriter, checked against the live profanity `WordFilter` read per rewrite (`HeadingRewrite::words`), `ReminderCardStore` records written before the claim); `pregen.rs` (`HeaderPregen`, its own serve worker) rewrites them ahead of time: a daily batch at the live `notifications.header_generation_time` (guild zone, default 00:00; a process past today's time without a batch runs one at once; a changed time applies from its next occurrence) covers every card firing in 24 h with no cap, records every key it saw within 8 days, and a 60 s catch-up tick rewrites only keys the batch had not seen (≤4 per tick) and retries the batch's failures (3 attempts per key; a busy permit retries without spending one, ≤30 times). Rewrites-log stages `batch`/`catchup`; 30 s deadline, insert-if-absent, no lock across the call, a stored line never rewritten, so the send path never calls the model: it reads the stored line or stores the seed, which then wins; `refresh.rs`: the store's run-write observer feeds a coalescing `RefreshQueue`; one serve worker edits posted reminder cards and the week's digest (never re-uploads art). Art lookups block: go through `fetch_art` (blocking pool), never call `ArtSource::find` on the runtime. `preview.rs` is the admin card preview: a posted card as the refresh edit builds it (`refresh::posted_content`/`posted_mentions` over its `posted_cards` row and record), an unsent one via `plan_dispatch` at its fire time with only unsent siblings and the stored record's heading if any, all through `cards::build`; it must stay free of writes, model calls, art reads and Discord calls.
- Run completion (`delivery/run_prompts.rs`, v5 deviation from the tick order above): `mark_done` is replaced in the tick by `complete_runs` (every live run past its completion cutoff → `finish_run` as `system:delivery`, request id `run-outcome:<run>:auto-done:<unix>`; it also finishes a claimed press whose settle was lost; a run staff reopened after its end, `completion::reopened` (status pin set at or after the end, written in every attendance mode, cleared by a move), is skipped and never frozen, user rule 2026-10-26), and `run_prompts_in` runs after ownership requests (close asks of runs ended/moved/gone, re-plan moved runs, open due asks, post them once by source key `run-prompt:<run>:<ask>` (a bound but unrecorded post is recovered with `bound_source`), edit closed asks into their outcome). The tick never calls `Delivery::mark_done`. Prompts are V2, ping nobody, and their status changes are unannounced. Presses (`run:done|missed|later:<run>:<ask>`, `commands/run_prompt.rs`) bypass the `/status` bossing gate and require the run's party or staff; the ask is claimed first (one winner), then `Writer::settle_run` re-checks live/unmoved/allowed in the commit.
- `delivery/manual.rs` (`ManualRewrite`, its own serve worker; `/debug rewrite` and `POST /api/admin/headers/rewrite` share it through `api::state::HeaderRewritePort`) is the one exception to "a stored line is never rewritten": single-flight (a second trigger while one is queued or running is refused), it rewrites every bound card of the current boss week naming a run still ahead (day-of only in the classic style) and the week's active digest, sequentially through `HeadingRewrite` (stage `manual`, 30 s, ended by the worker's stop). An accepted line is appended to the store's insert-only header overrides, which every heading/phrase read returns, and the post is edited through `CardRefresh` (no new post, ping or upload); a rejected or failed rewrite stores and edits nothing.
- Message style (`notifications.message_style`, read live through `CardKit::style`) is presentation only and independent of the attendance mode: `classic` must stay byte-exact (`tests/delivery/redesign/classic_cards.json`, never regenerate it to absorb a change); `redesigned` cards live in `delivery/cards/redesign/` (shared vocabulary in `vocab.rs`, Discord limits in `limits.rs`). A card may carry several embeds; each distinct picture is uploaded once and edits only reference posted names.
- Estimate share chart (`delivery/estimates.rs`, drawing in `cards/chart/`): redesigned day-of and countdown **creates** only (the tick's dispatch and `/debug ping`), never classic, never an edit. `CardKit::estimates` (`PartyEstimates`, serve's `CachedEstimates` while modules `roster` and `character_data` with a scouter URL are on) reads each run's party through `domain::characters::PartyRoster` and `Estimates::cached` / `cached_party` only (stored results of any age; never starts a lookup); shares come from members' effective % only (`domain::chardata::PartyShares`). While `Estimates::looking_up` (asked per IGN) says a queued, running or waiting job (manual or background) covers a brought member with no stored result, there is no chart (`estimate_chart_skipped` `lookup_running`); a refresh of members who all have one draws what is stored. When the oldest reading used (party total included) is `Estimates::stale`, the "as of" line and the alt text add "older than n days" (`Chart::older_than`, n = `fresh_days`). The PNG is `estimate.png`, a plain attachment no embed names, so edits (which send no `attachments` field) keep it; never add an upload to an edit. It is attached beside the legacy "Open in portal" row (`shows_files`: text with no components or only `transport::legacy_rows`); only a V2 layout or an empty render goes without. Any failure (unreadable party, render error/panic, >2 s, too large, 10 files) posts the card without it and logs `estimate_chart_skipped`. The admin preview (`preview::reminder_chart`, `GET /api/admin/reminders/{id}/estimate.png`) goes through the same `chart_for`/`draw` with a `CachedEstimates` over the API's roster port, so keep `chart_for` free of writes, art reads and Discord calls. Fonts are the unmodified OFL TTFs in `cards/chart/fonts/` (`include_bytes!`, inside `src/` for the image build); the SVG is pinned by `tests/delivery/redesign/chart/*.svg` (`KANADE_WRITE_CHART=1` rewrites them only for an intended look change).
- Pinging posts with buttons (the ownership request, and the redesigned day-of and countdown cards' "Open in portal" link while the public portal is open, `redesign/portal.rs`) are legacy text with action rows (`transport::legacy_rows`, `MessageEdit::legacy`; `[]` rows clears the buttons, and every card edit with text sends its rows so the link follows the portal switch and the style); every other component post is V2.
- Components V2 (redesigned style only, never for pinging cards): the digest (`redesign/digest.rs`), `/schedule` (`redesign/schedule.rs`) and proposal cards (`cards/v2.rs`), on the shared builders and 40-component / 4,000-char budget in `redesign/v2.rs` (over budget = the embed). Which posts are V2 lives only in memory (`redesign/live.rs` `LiveFormats`, shared by every `CardKit` clone): a post keeps its format, unknown is legacy, and a 400 on a legacy edit triggers one flags read; Discord cannot drop the flag, so a V2 digest stays as posted after a flip back. V2 proposal cards carry Apply/Reject buttons instead of seeded ✅/❌; presses (`commands/components.rs`) run through the reaction worker and `CardDesk::on_press`, the same path as reactions, and reaction replay skips V2 cards.
- Named exception to V4_COMPAT's v4-exact card **text**: every Rust v5 day-of field lists only unknown-answer members as `Still to answer` beneath the tally, not the whole party. The top ping line still lists the party; V4_COMPAT scheduling, tally and mention rules remain v4. See `docs/notes/discord-adapter.md`.
- `guild_cache/`: channels, threads→parent, names, role permissions and the watch list (channels + categories), fed by the router; implements `api::state::ChannelList`, `chat::gate::ChannelDirectory` and notify reachability. Share ONE `Arc<GuildCache>` between the router, API, chat gate and tick. Events from other guilds and DMs are dropped and counted (`Router::dropped()`); never add a global-command call (a test greps for it).
- `handler/`: the serve `EventHandler` fan-out (`Fanout`: roster jobs, reactions, spawned interaction/registration tasks, message counters, the chat feed and the extraction `MessageFeed`; guild commands are bulk-overwritten on the first `GuildAvailable` after each `Ready`) and the sequential reaction worker (`Reactions`: card ✅/❌ → the one shared `Arc<CardDesk>`, else RSVP). A successful ❌ hands all-chat stored-card facts to chat's driver follow-up port; source/author/channel checks and cooldown stay there, so extraction cards and every failed scope remain silent. `roster/`: the one sequential `RosterTask` (gateway order; role pruning on `GuildAvailable`; `reconcile.rs` pages `list_members` and never concludes departures from a failed page) and `LiveRoster`, the in-memory member snapshot. Composed in `runtime::serve::discord`.
- `chat_feed/`: chat input and output. `ChatFeed` turns a created message into the driver's `Asked` from resolved lists only (member roles, mentions, the referenced message; never fetched) and deletions into cancels; `DiscordSurface` is the driver's effect adapter: reactions and one transport call per post (`SILENT` when asked), edit, delete or typing trigger, no mentions, outcomes mapped to `chat::driver::Effect`. It never retries and never splits: delivery (placeholder, parts, retries, marker) is `chat::driver::delivery`, outside the journal. The handler calls it inline, so keep it synchronous and short. Its verdict is the extraction feed's `handled_by_chat`.
- `extract_feed/`: gateway messages → the pipeline's `MessageEvent` in gateway order (loop guard kinds; older than 60 s = `Replay`, cached only; chat-handled messages and their later edits cached, never read) and `DiscordHistory`, the rescan backfill (`After` pages of 100, channel then cached threads).
- `cards/`: extraction proposal cards — `format.rs` (v4 card text, byte-exact), `desk.rs` (`CardDesk`: save `CardDetails`, post through the delivery `Executor` with `DeliveryTarget::Card`, re-render/refresh from stored details and proposal states, no mentions), `react.rs` (✅/❌ → `approve_proposal`/`reject_proposal`; `Authority` supplies the `Approver`), `outbox.rs` (`CardOutbox`, the extract `Outbox`). Approval rules live in the scheduler, never here.
- `cards/replay.rs` reconciles pending bound cards after each fresh READY's roster gate in the sequential reaction worker: complete both HTTP reaction sides first, ignore self/unauthorised users, note conflicts, and never send stale chat rejection follow-ups.
- `rsvp_replay/` follows proposal replay in that worker (fresh READY only; RESUMED and delivery gating unchanged). `ReplayCards` separates recent bound evidence from all mapped cards; removals require complete reads and the bot's matching reaction on every mapping. Keep the pre-HTTP RSVP/slot/status `Versioned` expectations, provenance guards and post-drain start check; never route replay through decline effects. Bounds: 40 distinct messages, 8 cards/run, 2 pages/side/type, 7-day evidence age, 3 live-event restarts. Extraction's first answer write carries `extract-answer:` even if its later chat-source write fails.
- `identity/`: after each `READY` and the bot's own profile changes (`GuildCache::profile_changes`), fetch its avatar/banner (`current_user` + CDN, `cdn.rs`) into `KANADE_IDENTITY_DIR` by temp + rename (`files.rs`); cosmetic, failures only log. Spawned as a worker in `runtime::serve::discord`.
- Character data (module `character_data`): `commands/character/` (`/character link|unlink|data|share`, `Gate::Anyone`, deferred ephemeral, registered by `register_character` after `register_retained` only while the module is on; the notice's `chardata:link:<notice>:<issued>:<cid>` / `chardata:cancel:<cid>` buttons come back as `link_press`/`cancel_press` and replace the notice through `Dispatcher::update_pressed`) and `chardata/` (`copy.rs`: the approved board copy, exact words, every Nexon card ends with `ATTRIBUTION`, the stub has none; `posts.rs` `DiscordPosts`: share cards are created through the transport after the `posts` row is written, an ambiguous create is searched by ref in the last 50 messages twice and never resent, and it is the `PostDesk` the `CharacterData` task strips through). All reads go through `CharacterData::member_characters` (`current_link`/`data`); tests: `tests/discord/slash/character.rs`.
- `guides/` (module `guides`, `Publisher`, its own serve worker, also the API's `GuidePort`): single-flight; claims the oldest queued run, re-reads the channel (`inspect.rs`: grants from the guild cache incl. attach files, one `Latest` page of 100, presence for slots the page cannot vouch for, within `INSPECT_BUDGET`), re-renders the saved guide through the API's `GuideFiles` adapter and runs the plan only if its hash is the confirmed one (else `plan_changed`, nothing sent; a grants-blocked plan stops `rejected` before any call). Creates go through `Executor::execute_source` (source `guide-post:<op uuid>`, `EffectKind::GuideSlot`, `SILENT`, no mentions, files on create only); an unconfirmed create is never resent but searched (`reconcile.rs`: `bound_source`, then the bot's own message newer than every earlier slot showing the same content/embeds, 2 × 50 messages; one match recovered, none/several unknown and the run stops). Edits keep files (an edit's 404 marks the slot gone, `plan_changed`; ambiguous: one retry); deletes are confirmed by Discord or `message_presence`, unconfirmed stops before any create. Cancel and stop are read between ops; a create cut by shutdown stays `pending` and `recover` (after the journal's `recover_on_start`) settles it on the next start. Worker calls carry a 30 s deadline; creates rely on the transport's own (cutting the executor mid-journal would strand the claim).
- Never log tokens: interaction tokens and bot tokens are redacted in every `Debug`. `ids.rs` parses canonical snowflakes only.
- Shutdown tracks and aborts the actual interaction task, not a wrapper awaiting its `JoinHandle` (aborting the wrapper detaches the command). Share one bounded task-drain deadline, join aborted tasks before closing the store, and gate the first delivery tick on completed roster reconciliation.
- A bound delivery claim survives native row retirement: replace a digest only after confirmed remote deletion, then atomically retire the exact bound attempt, release its target with actor and reason, and retire the native row under the same live lease; an ambiguous deletion suppresses replacement.
- Contract: `docs/notes/discord-adapter.md`. Checks: `cargo test --all-features --test discord` (and `--test delivery`).
