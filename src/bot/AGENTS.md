# Discord adapter guide

- `/style` choices, autocomplete and validation read the live published-profile list; a saved private choice is retained but unavailable and chat falls back to the bundle default.
- Twilight-based and storage-independent: persistence and scheduling are reached only through traits (`CardIndex`, `ReactionSink`, `DeliveryJournal`, `SchedulerService`).
- `transport/`: the `DiscordTransport` trait (`mod.rs`), `TwilightTransport` (`twilight.rs`: 10 s attempt / 30 s call / 2.5 s interaction-response deadlines, ≤4 sends per call), `FakeDiscord` (`fake.rs`, test-support). Every call returns `Delivered`, `DefinitelyRejected` or `Ambiguous` (`outcome.rs`); an ambiguous create may have posted and must never be replayed. Connect failures are `NotSent`. `create_flagged_message` (only `CREATE_FLAGS`; `SILENT` for chat placeholders) and fire-and-forget `trigger_typing` default to `Invalid` unsent: any wrapper transport must delegate them (serve's `LateTransport` does). `FakeDiscord::hold(op)` parks a call mid-flight for tests.
- `mentions.rs` is the only way to build allowed mentions: explicit valid user IDs only, never `@everyone`/roles/replied user; an empty list pings nobody.
- `gateway/`: least-privilege intents matching v4 (`intents.rs`), single-shard `runner.rs` with graceful drain, `close.rs` fatal close reasons (4004, 4010–4014), `status.rs` the connection state health reads (`run_live` takes a prepared router + status). `events/`: guild-scoped routing, ✅/❌ reactions → RSVP via `CardIndex`, roster updates. `EventHandler::handle` runs inline — keep it short and move Discord I/O to `commands::spawn_interaction` or tasks.
- `commands/`: guild registration payloads (`build.rs`), v4 permission gates (`access.rs`), dispatcher with ephemeral refusals, deferred replies, gated autocomplete and redelivery dedupe, and the retained v4 commands (`register_retained`; user decision 2026-09-25). Handlers read through `CommandContext` and write only through the API's shared `Writer` as `member:<id>`/`Surface::Discord` with the interaction id as request id; notices come from the scheduler's outbox, never posted here. Replies keep v4 texts (`text.rs`); `/rescan` answers "not available" until its port is wired; `/debug ping`/`clear_test` go through `delivery::DebugDesk` (`delivery/debug/`: journalled `debug_card` effect, `DeliveryTarget::DebugCard`, `debug_cards` rows); `/limits` reads the chat pilot's allowance.
- `delivery/`: `tick.rs` runs v4's order (materialise on rollover → mark_done → attendance recount (V5 only) → draft expiry → notice outbox drain (`notices.rs`) → digest → dispatch) with one clock read and one lease per tick; dispatch and the notice drain each have their own cap (`max_sends_per_tick`) on claimed sends; `executor.rs` maps outcomes to the journal (Delivered→`bind` with the channel actually used, Ambiguous/bind error→`mark_indeterminate`, NotSent/RateLimited→`release_unsent`, other rejections→`retire_rejected` + alert) and replaces a digest only after confirmed deletion; `alerts.rs` throttles identical admin alerts per hour (`LogAlerts` is the serve destination: structured log); `ports.rs` adapts stores/clock. One failing send never aborts the tick (only lease/backend loss does). Auto-checkpoint and draft expiry failures never abort it either: they raise throttled `CheckpointFailed` / `DraftExpiryFailed` / `AttendanceRecountFailed` alerts and retry next tick. Notices are written to the store's notice outbox by the deciding commit/close itself; `notices.rs` drains them through `Executor::execute_source` (journal `claim_source`, keyed by `(source, ordinal)`), so never enqueue returned notices again. `notice_text.rs` renders them (v4's notice texts byte-exact for the kinds v4 announced); stale (`max_notice_age`), silent and undecodable rows are handled per row and never abort the tick. Rendering and mentions follow `DeliverySettings.attendance`: V4_COMPAT is v4 exactly; V5 adds tallies/expected and morning pings to unknown members only (`docs/v5/attendance.md`). Reminder/digest cards live in `delivery/cards/` (v4 `day_of_card`/`countdown_card`/`digest_card`, art via `ArtSource`, the persona-voiced day-of heading via the nudge rewriter, `ReminderCardStore` records written before the claim); `refresh.rs`: the store's run-write observer feeds a coalescing `RefreshQueue`; one serve worker edits posted reminder cards and the week's digest (never re-uploads art). Art lookups block: go through `fetch_art` (blocking pool), never call `ArtSource::find` on the runtime.
- Named exception to V4_COMPAT's v4-exact card **text**: every Rust v5 day-of field lists only unknown-answer members as `Still to answer` beneath the tally, not the whole party. The top ping line still lists the party; V4_COMPAT scheduling, tally and mention rules remain v4. See `docs/v5/discord-adapter.md`.
- `guild_cache/`: channels, threads→parent, names, role permissions and the watch list (channels + categories), fed by the router; implements `api::state::ChannelList`, `chat::gate::ChannelDirectory` and notify reachability. Share ONE `Arc<GuildCache>` between the router, API, chat gate and tick. Events from other guilds and DMs are dropped and counted (`Router::dropped()`); never add a global-command call (a test greps for it).
- `handler/`: the serve `EventHandler` fan-out (`Fanout`: roster jobs, reactions, spawned interaction/registration tasks, message counters, the chat feed and the extraction `MessageFeed`; guild commands are bulk-overwritten on the first `GuildAvailable` after each `Ready`) and the sequential reaction worker (`Reactions`: card ✅/❌ → the one shared `Arc<CardDesk>`, else RSVP). `roster/`: the one sequential `RosterTask` (gateway order; role pruning on `GuildAvailable`; `reconcile.rs` pages `list_members` and never concludes departures from a failed page) and `LiveRoster`, the in-memory member snapshot. Composed in `runtime::serve::discord`.
- `chat_feed/`: chat input and output. `ChatFeed` turns a created message into the driver's `Asked` from resolved lists only (member roles, mentions, the referenced message; never fetched) and deletions into cancels; `DiscordSurface` is the driver's effect adapter: reactions and one transport call per post (`SILENT` when asked), edit, delete or typing trigger, no mentions, outcomes mapped to `chat::driver::Effect`. It never retries and never splits: delivery (placeholder, parts, retries, marker) is `chat::driver::delivery`, outside the journal. The handler calls it inline, so keep it synchronous and short. Its verdict is the extraction feed's `handled_by_chat`.
- `extract_feed/`: gateway messages → the pipeline's `MessageEvent` in gateway order (loop guard kinds; older than 60 s = `Replay`, cached only; chat-handled messages and their later edits cached, never read) and `DiscordHistory`, the rescan backfill (`After` pages of 100, channel then cached threads).
- `cards/`: extraction proposal cards — `format.rs` (v4 card text, `docs/v5/vectors/extract/cards.json` byte-exact), `desk.rs` (`CardDesk`: save `CardDetails`, post through the delivery `Executor` with `DeliveryTarget::Card`, re-render/refresh from stored details and proposal states, no mentions), `react.rs` (✅/❌ → `approve_proposal`/`reject_proposal`; `Authority` supplies the `Approver`), `outbox.rs` (`CardOutbox`, the extract `Outbox`). Approval rules live in the scheduler, never here.
- `identity/`: after each `READY` and the bot's own profile changes (`GuildCache::profile_changes`), fetch its avatar/banner (`current_user` + CDN, `cdn.rs`) into `KANADE_IDENTITY_DIR` by temp + rename (`files.rs`); cosmetic, failures only log. Spawned as a worker in `runtime::serve::discord`.
- Never log tokens: interaction tokens and bot tokens are redacted in every `Debug`. `ids.rs` parses canonical snowflakes only.
- Contract: `docs/v5/discord-adapter.md`. Checks: `cargo test --all-features --test discord` (and `--test delivery`).
